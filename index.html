황성주

Hadoop 위에서 Hive와 Spark SQL로 데이터를 다루고, 데이터를 쓰는 사람의 질문에 맞춰 마트를 설계하고 운영하는 데이터 분석 엔지니어입니다.

보험사 Data Lab에서 장기 TM 본부 약 300명이 매일 보는 상담사 실적 마트와 5개 조직이 쓰는 보험 실적 마트를 만들었습니다. 그 마트에 데이터를 대는 CDC 파이프라인(하루 약 10억 건, 테이블 약 290개)도 직접 다시 설계해, 적재 시간을 절반가량 줄이고 실패를 없앴습니다. 분석가가 배치를 직접 확인하고 다시 돌릴 수 있게 Airflow 이관과 가이드도 맡았습니다.

P1

TM 상담사 활동·실적 집계 마트

기준 날짜가 서로 다른 통화 활동과 청약 실적을 상담사 × 월 단위로 맞춘 집계 마트를 설계했습니다. 장기 TM 본부 약 300명이 쓰는 대시보드에 하루 여러 번 공급하고 있습니다.

배경

장기 TM 본부가 상담사별 배정과 통화 활동, 청약 실적을 한 화면에서 보고자 했습니다. 원천은 Oracle DB의 통화 로그, 고객 DB 배정, 청약, 상담사 정보입니다.

문제

  • 활동(통화 로그)과 실적(청약)의 기준 날짜가 달라, 한 날짜로 조인하면 어느 한쪽이 빠졌습니다.
  • 실적이 없는 달의 상담사가 집계에서 사라져 월별 인원과 추이가 맞지 않았습니다.
  • FIRST_VALUE에 상담사 단위 파티션이 없어 최종 영업 상태가 모두 같은 값으로 나왔습니다.
  • BI 데이터셋 안의 윈도우 함수가 GROUP BY 오류를 냈습니다.

구조

    활동일자와 청약일자를 독립 컬럼으로 둠

  3. 기준 틀

  4. 소비 마트

    윈도우 계산까지 마트에서 끝냄

  5. 대시보드

    장기 TM 본부 약 300명

    하루 여러 번 갱신

집계 단위실적 테이블 기준 집계상담사 × 월 기준 틀을 먼저 만들고 실적을 LEFT JOIN. 실적 없는 달도 0으로 보여 인원 수가 맞습니다.

P3

Oozie → Airflow 배치 이관과 리니지

서로 얽힌 Oozie 배치 약 190개의 의존성을 추출해 리니지와 영향 범위를 먼저 만들고, 그 순서대로 Airflow로 옮겼습니다. 어떤 배치를 바꾸면 어떤 마트가 영향을 받는지 추적할 수 있게 됐습니다.

진행 순서

  1. 코디네이터 간 선후 관계를 스크립트로 추출해 리니지 표를 만들고, 그래프 탐색으로 배치를 바꿀 때 영향받는 하위 배치와 마트를 계산했습니다.
  2. 의존성 순서대로 DAG를 자동 생성해 수작업 이관 오류를 줄였습니다.
  3. 한국 시간 기준 스케줄이 이중으로 밀리던 오류와 크론 표현식 오류를 바로잡았습니다.
  4. 데이터 분석가용 Airflow 사용 가이드를 작성해 배포했습니다. 분석가가 직접 배치를 확인하고 다시 돌릴 수 있게 됐습니다.

P4

SQL·Spark 배치 최적화

실행 계획을 읽고 조인, 셔플, 파일 크기, Executor 자원을 조정해 대용량 배치를 안정화했습니다. Hive(Tez) 배치를 Spark로 전환해 평균 배치 시간을 2시간에서 30분으로 줄였고, Oracle 파이프라인의 임시 테이블을 57개에서 17개로 정리했습니다.

문제

Hive와 Spark 기반 ETL에서 조인과 집계가 많아 셔플 병목, 데이터 쏠림, 작은 파일 과다 생성, 메모리 압박이 반복됐습니다.

한 일

  1. 실행 계획을 분석해 브로드캐스트 조인 대상을 고르고 불필요한 셔플을 없앴습니다.
  2. 셔플 파티션 수를 다시 정하고 출력 파일 크기를 맞춰 작은 파일을 줄였습니다.
  3. Executor 코어와 메모리를 조정해 동시 실행 수를 제어하고 GC를 줄였습니다.
  4. Spark가 쓴 Parquet과 Hive DDL의 DECIMAL 인코딩 차이로 생긴 읽기 오류(ParquetDecodingException)를 찾아 해결했습니다.
  5. Oracle 파이프라인에서 한 번만 참조되는 임시 테이블을 CTE로 흡수해 57개를 17개로 줄였습니다.

결과

  • Hive(Tez) 배치를 Spark로 전환해 평균 배치 시간 2시간 → 30분 (인턴 시기)
  • 데이터 쏠림을 완화해 배치 실행 시간의 편차를 줄임
  • Oracle 파이프라인 임시 테이블 57개 → 17개

플러그 부정사용 탐지 대시보드

탐지 기준

  • 사고 신고가 있다는 건 그날 차가 실제로 운행됐다는 뜻입니다.
  • 그런데 사고일 기준 전후 1일 동안 주행 기록이 없다면, 플러그를 뽑고 운행했을 가능성이 높다고 보고 의심 건으로 분류했습니다.
  • 서로 다른 두 데이터(보상의 사고 신고, IoT의 주행 기록)가 어긋나는 지점을 근거로 삼아, 고객의 자기 신고 없이도 이상 행동을 찾을 수 있게 했습니다.

마트를 설계할 때 지키는 것

  • 조인하기 전에 행 하나가 무엇인지부터 정합니다.

    상담사 마트에서 인원이 맞지 않았던 건 쿼리 실수가 아니라 집계 단위를 정하지 않고 시작했기 때문이었습니다.

  • 계산은 소비하는 곳이 아니라 마트에서 끝냅니다.

    BI 툴에서 계산하면 도구 제약에 걸리고, 화면마다 숫자가 갈라집니다.

  • 병렬보다 격리가 먼저입니다.

    빠르게 도는 구조보다, 하나가 실패해도 번지지 않는 구조가 결국 더 빨랐습니다.

  • 숫자는 대조와 검수를 거쳐야 신뢰를 얻습니다.

    기존 보고 자료와 맞춰 보고 현업 검수를 받은 뒤에야 마트가 실제로 쓰였습니다.
